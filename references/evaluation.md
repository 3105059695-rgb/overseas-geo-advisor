# 开发检查与内容验收

`tests/development_questions.json` 提供40个开发问题和必须/禁止事项。它是问题覆盖资产，运行工具没有异常不代表40题回答已经合格。

对每题分别记录候选检索、最终证据包、AI最终回答：

1. **候选证据召回：** 必需证据是否进入候选，不因同源多个文件重复计分。
2. **最终证据包覆盖：** 真正用于回答的片段是否保留方法、结果、条件与限制。
3. **事实支持：** 每项事实是否由原文支持，数字是否保留分母和时间。
4. **推导合理性：** 建议是否具有足够前提，业务条件是否成立，不确定性是否明确。
5. **主结论门槛：** 任何核心建议或优先级无依据，或遗漏足以改变建议的条件，都不能用整体95%支持率掩盖。
6. **用户结果：** 概念解释是否让用户理解；操作解释是否让用户明确下一步及所需材料。

程序验证只记录结构与资格，语义评分由对照原文的内容核验完成。当前源样稿由AI读取资料整理，尚未经独立领域专家验收。不要在报告中写成人工专家已审核。

## v0.4 的真实问题回归

必须包含用户真实问法，不只测试命中预写样稿的三道题：

- “海外的不同 AI，他们喜欢的信源是什么？”
- “我想知道 Claude 或者 Grok 他们的信源到底是什么。”
- “Claude 和 Grok 联网回答时分别从哪里找资料、引用什么来源？有没有依据说明它们偏爱哪些网站？”
- 分别单独问 Claude、Grok，并用英文改写同样的问题。

每次保存问题、知识版本、实际通道、返回候选、回读段落、最终答案和采用/剔除理由。以下任何一项失败，都不能报告这道题通过：

| 维度 | 可观察的通过条件 | 典型失败 |
|---|---|---|
| 对象匹配 | Claude 与 Grok 分别有依据或明确的本次缺口 | 国内官媒/豆包清单成为 Claude 的直接证据；只回答其中一个产品 |
| 问题匹配 | 先解释用户问的来源/渠道；只有问偏好时才要求相应统计 | 把“信源是什么”换成一篇其他 AI 的引用重合率报告 |
| 引用支持 | 采用的段落真的支持该平台该项说法，并保留模式与日期 | 用“建议 Grok 开放搜索”证明 Grok 已经具有某检索机制 |
| 小白理解 | 先直接解答，必要术语有普通中文解释，事实和例子分开 | 开头全是论文缩写、运行日志或哈希，读者看不出答案 |
| 诚实覆盖 | 查阅说明只计算实际读过和采用的资料，缺口限定本次范围 | 看前 10 条就说已读完全部，或把程序分组当人工核验的独立证据 |
| 连接与答案分开 | 记录 GitHub/MCP、回读成功和逐项语义判断 | 仅 status 返回文档数就宣称“引用成功、回答正确” |

回归应保留一份原文中没有目标平台依据的负例，确认系统不会为凑答案把背景升级成直接证据。关键词与邻近关系规则降低误检，但不能给出普遍语义正确率；最终答案仍由连接它的 AI 编写，豆包等具体客户端的展示需要单独实测。

独立40题应由未使用其答案调试的内容负责人准备，按问题意图、证据组合和业务条件与开发题区分，不能只换措辞。记录知识版本、模型、客户端和提示词版本。单独报告各题型分子/分母，以及真正经过GUI客户端展示验证的范围。

首版拟议指标沿用评审计划：候选Recall@20和最终关键证据覆盖≥90%、事实支持≥95%、必要要点完整性≥90%、引用可定位100%；主结论和重要优先级证据缺失为阻断项。这些是未来验收目标，不是当前自动脚本已测得的结果。

内容投入应按文章、论文、评论、表格/OCR分别记录实际核对时间后估算。先测少量样本，再承诺全库审核排期；30天动态资料核查、90天方法复查可作为待评审安排，由明确负责人维护。逾期动态信息只能作带日期的历史说明。
