# 证据使用与回答规则

## 资料可找到与结论可采用分别判断

文档整体状态只用于导航。每项关键断言还要核对真实原文、含义、日期、条件和证据性质。用户要求专业详细问答时，先确定这些范围，再写答案。

## 先匹配问题，再判断证据

把用户的问题拆成“对象 + 想知道的关系”，而不是只找重复关键词。例如“Claude 和 Grok 的信源是什么”需要找到这两个产品与检索渠道、实际来源的关系；国内官媒清单、使用 Claude 写 SEO 文章的方法、建议 Grok 未来开放搜索的帖子，都不能据此回答其实际信源。

“有哪些来源”“哪类来源更常被引用”“从哪里检索”“训练时用了什么”是不同问题。优先回答用户实际问的层次；不因为缺少引用份额研究，就跳过已有依据的渠道说明。也不把“能检索某类内容”写成“最喜欢某类内容”。

远程结果中的 `query_intent`、`answer_brief` 是程序提示；`relevance.tier=direct_candidate` 只表示通过词法与邻近关系筛选，仍须读原文。`background_citations` 不支撑目标产品的主结论。`platform_coverage` 是本次返回结果的覆盖，不是全库已读证明。一个段落提到多个平台时，只把支持该平台的句子或表格行用于它；`direct_platforms` 也需人工式语义核对。

对多个对象分别建立待答项，不能用 Claude 的证据回答 Grok，或用 ChatGPT 的研究补足缺口。必要时拆开查询并加入中英文别名、web search、citations、sources 等与问题相符的术语。有限次改写仍没有证据时，保留具体缺口，不不断扩展话题。

| 实际核验范围 | 允许使用 | 禁止升级 |
|---|---|---|
| 原文片段和具体定义已核对 | “该来源按以下口径定义……” | 所有研究/所有产品统一采用该定义 |
| 确认作者在某条件下报告经验或实验 | “作者在……条件下报告……” | 已独立验证有效、所有用户都能获得同样效果 |
| 确认历史产品提及或历史机制 | 指定资料时期的说明 | 当前可用性、当前供应商关系、当前完整名单 |
| 关键数字、原文含义或机制未核对 | 查证线索、补充阅读、明确的待核实问题 | 核心数字、现行机制、渠道投入优先级 |
| 存在足以改变结论的争议或条件缺失 | 分别解释不同说法，说明无法确定 | 擅自挑一个更肯定的答案 |
| 用户提供的页面、日志和观察 | 标为“根据你提供的材料”并限定推断 | 冒充独立测量或完整站点审计 |

程序已确认 exact quote 在原文中出现，只能证明文本对应。它不能独立证明文章事实真实或方法有效。

## 核验范围要具体

可使用以下描述：出处与正文匹配、引用段落准确、译文语义核对、发布日期核对、实验条件已读、数字分母已读、原论文相应部分已读、独立证据已核对。不要用笼统“已验证”覆盖所有维度。

本 Skill 种子断言的核验范围记录在 `assets/curated.json`。检查声明的原始片段是否匹配当前入库版本；不匹配时不可套用原来的资格。

对新的问题，不必把整个文档笼统设为可信。默认由 `workflow prepare` 回读相应版本，必要时用 `geo.py read` 补读上下文，再执行 `workflow adjudicate` 与 `workflow check`。按[新版合同](workflow-v0.5.md)提交陈述、连续原文摘录、引用和条件；逐句语义判断仍由回答者完成。仅明确选择旧 MCP 时才使用 `read_geo_source`、`check_geo_answer`；它们不能代替新版工作流。

仅在本地模式，才向 `review_geo_claim` 提交 statement、exact_quote、allowed_use、conditions、review_note。工具只允许 `attributed_report`、`definition`、`historical`，核对片段与版本，并在本机派生数据库中记录本次 AI 的含义核对声明。它不会修改原文或种子资料。

登记后的断言必须保持限定归因，且注明未独立验证。该登记不是领域专家审核；语义是否匹配不能靠字符串存在来证明。review_note 应写实际判断理由和适用边界，不写“已检查”这样的空话。涉及当前机制、效果保证或行动排序，不能用这个接口获取更高资格。

## 主结论与建议的门槛

每项主结论以及“先做哪一项”的建议至少回答：

1. 它依据的事实或作者报告是什么？原文在哪？
2. 用户的已知条件是否匹配？哪些是尚未确认的假设？
3. 为什么这些前提足以支持建议？是来源明确建议，还是本次综合推导？
4. 什么条件会改变建议或顺序？

不能用许多正确背景知识掩盖一个没有依据的核心建议。引文多、相关性高、资料最近收藏都不能自动提高结论资格。

涉及推广材料里的渠道份额或效果数字，先核对原始研究、指标、分母、样本、时间和平台。缺少这些时，数字只作为待核实线索。

## 证据包和上下文

检索候选不等于最终证据。最终送入回答的内容应覆盖必答要点与必要条件。对同一论文，方法、结果、局限分别保留；只删除重复文字或重复片段，不把每篇来源强制压成一个片段。

同一研究的论文、中文译文、整理笔记和转载共有一个来源链。综合判断需要关注独立证据，而不是文件数量。

原始帖子及评论出现否定、反讽或分歧时，保留问题和父回复的上下文。原始文本被截断时说明限制，不把截取段落视作完整讨论。

## 逐项核对

程序层负责引用ID、文档版本、行号、片段存在、使用资格等结构性判断。

语义层由实际回答的AI对照原文检查：相关性、蕴含关系、限定条件、数字单位、事实与推论区别。未核验事实只做线索。语义层自检仍可能出错，不能报告成独立人工验收。

组织答案前，按新版合同保留 `claim`、`kind`、`citation_id`、`relation`、`conditions` 与判断理由；草稿逐条映射到已采用陈述。旧接口的 `text/main/citation_ids/allowed_use` 仅用于历史兼容。文件由 AI 准备，不是要求用户填写的表单。

再保留支持它的 `exact_quote`，检验以下三点：

- 原文是否真的谈这个对象和这项关系，而不只是出现同样的名字？
- 原文是在陈述事实、转述他人、提出建议、假设，还是反问？回答应保持相同性质。
- 如果删除引用前后的限制，结论是否会变强？会变强就把限制带回正文。

用户看到的引用应靠近结论，用来源标题、日期和短摘录解释“这份资料为什么支持这句话”。英文摘录可配简短中文解释，翻译标为译文；不把整段 JSON 或长哈希当成读者能理解的依据。来源列表不能代替逐项对应。新版 `workflow check` 通过或旧 `check_geo_answer` 结构通过，都不应显示成“答案已独立审核”。

## 失败与未知

出现不足时明确说缺什么，不用通用记忆填补并归因给知识库。可以给用户一个可执行的补证据清单，例如目标平台、观察日期、查询样本、实际回答、相关网页和日志。

缺口限定到本次检索与实际回读范围。未读完全部相关版本时，不说“已读完所有资料”“知识库完全没有”“这是唯一研究”。只找到背景资料时直接说明它不支持哪项结论；不要长篇复述这些背景来代替答案。检索和读取成功时如实报告通道，但不因此声称引用支持已通过。

默认先查库，不借用模型记忆填补。需要当前事实核查时，使用当前 AI 已具备的联网工具打开原始来源，库外补充单独标注来源与核查日期，不能伪装为已入库资料。用户明确限定只用知识库或禁止联网时遵守；没有联网能力时如实保留当前事实缺口。

如果用户只要通用排查，说明这是可能原因和检查顺序；若要具体归因，缺少现场证据时不作确定判断。

没有完整时间核查的产品资料，回答“知识库的已收录资料中提到……”并说明日期范围。不能因为问句含“现在”就自动把历史信息改写为现状。
